# TASK — Инициализация документации проекта audi-club.md

> Это задание для Claude Code. Выполняется в самом начале проекта, до/во время первых коммитов кода.
> Владелец — Валера, не программист; весь код и документацию пишет Claude. Язык общения и всех документов — русский.

---

## 0. Контекст

Это первый из трёх клубных сайтов на общем движке (audi-club.md, следом vw-club.md и skoda-club.md — каждый в своём репозитории, свой cPanel-хостинг). Пилот — audi-club.md.

Проект — «дочерний» по духу к уже существующему `bravo-motors.md`: тот же стек (Astro, Keystatic только локально, деплой по FTP через GitHub Actions на push, рабочий цикл через GitHub Desktop), но **другой репозиторий, другой сайт, другая аудитория** (не сервис, а клубное медиа с интеграцией в Facebook-сообщество ~100k участников и партнёрской ссылкой на bravo-motors.md как официальный сервис-партнёр).

В корне репозитория должен уже лежать (или появиться в ходе этой же сессии) бриф `BRIEF_audi-club-md.md` — исходное ТЗ пилота. Прочитай его первым делом, если он есть в репозитории. Если его нет — сообщи владельцу и останови задачу до его получения: без брифа документы будут пустыми по содержанию.

---

## 1. Что нужно сделать

Создать в корне репозитория **два живых документа**, по канону, уже отработанному на `bravo-motors.md`:

1. **`PROJECT_MAP.md`** — паспорт проекта, точка входа для любого нового экземпляра Claude без контекста.
2. **`DECISIONS.md`** — журнал решений в формате ADR (Architecture Decision Record).

Оба документа — не разовая выгрузка, а **инструмент, который ведётся на протяжении всего проекта**. Раздел 4 ниже описывает, как их поддерживать дальше.

---

## 2. Канон `PROJECT_MAP.md`

Используй как образец структуру `PROJECT_MAP.md` проекта bravo-motors.md (он должен быть доступен тебе как референс — попроси владельца приложить, если не приложен). Разделы, адаптированные под audi-club.md:

1. **Шапка** — дата актуальности, короткая памятка «владелец не программист, код пишет Claude, язык — русский», ссылка на то, что это точка входа и весь репозиторий читать не нужно.
2. **§1. Что за проект (одним экраном)** — клубный сайт Audi Club Moldova: бренд-медиа + партнёрская витрина bravo-motors.md, двуязычный (RU/RO), стек Astro, статика в проде, движок общий с vw-club.md/skoda-club.md (скопирован в репозиторий, не submodule/пакет).
3. **§2. Структура репозитория** — сгенерировать реальным деревом (`tree -L 3 -I 'node_modules|dist|.git'`), не выдумывать.
4. **§3. Где какая логика лежит** — таблица «Логика → Файл → Заметки», аналогично bravo-motors (i18n-карты, canonical/hreflang, крошки, дизайн-токены в `Layout.astro`, контент-коллекции `models`/`news`/статей «Журнал», JSON-LD страниц, деплой). Дополнительно отметить то, чего в bravo-motors не было: content-модель статей (frontmatter model/engine/years/type), авто-генерируемые страницы `/models/[model]/`, партнёрский блок со ссылкой на bravo-motors.md.
5. **§4. Карта документов** — таблица «Документ → О чём», включая сам `BRIEF_audi-club-md.md` как исходное ТЗ, `PROJECT_MAP.md`, `DECISIONS.md`, `DESIGN.md` (если/когда появится дизайн-система клубного бренда — премиум/тёмный с красным акцентом), контентные документы (6 стартовых статей и далее).
6. **§5. Задача → какие файлы просить** — тот же принцип онбординга: под конкретную работу просить только нужный минимум файлов, не весь репозиторий.
7. **§6. Рабочий цикл** — идентичен bravo-motors (правки → `npm run dev` → проверка → GitHub Desktop Commit → Push → Actions деплоит по FTP), с уточнением конкретного домена/хостинга audi-club.md, если отличается.
8. **§7. Подводные камни** — специфичные для этого сайта вещи, которые будущий Claude без контекста не увидит из кода: это витрина/медиа, а не сервис (не путать тон и цели с bravo-motors.md); сайт read-only — без логинов и «гаража»; движок общий с двумя другими клубными сайтами, но копируется, а не подключается пакетом — изменения в движке нужно переносить руками в остальные репозитории; сохранённый существующий логотип клуба (только оттенок красного подгоняется под акцентный цвет сайта); партнёрские промокоды (AUDICLUB15 и аналоги у других клубов) как часть контентной модели, не хардкодить текст промокода в разметке нескольких мест.
9. **§8. Поддержание карты в актуальности** — как в bravo-motors: дерево §2 регенерировать из репозитория, §3/§5/§7 обновлять построчно при архитектурных изменениях.

Если для заполнения конкретного раздела не хватает информации (например, финальная структура репозитория ещё не создана, домен хостинга не подтверждён, дизайн-система не готова) — оставь раздел с пометкой `TODO: уточнить у владельца` вместо того, чтобы придумывать содержание.

## 3. Канон `DECISIONS.md`

Используй как образец `DECISIONS.md` проекта bravo-motors.md — формат ADR: **Дата / Статус / Контекст / Решение / Последствия / Источник**, со сквозным индексом-таблицей в начале файла и нумерацией `ADR-0001`, `ADR-0002`, ...

Отличие от bravo-motors: там журнал реконструировали задним числом из чатов и коммитов. Здесь у тебя есть уникальная возможность **вести журнал с нуля, в реальном времени**, начиная с уже принятых на этапе брифинга решений. Подними из `BRIEF_audi-club-md.md` (и из истории обсуждения, если она доступна) уже принятые решения и оформи их как первые записи журнала, например (список ориентировочный — сверить с реальным брифом):

- архитектура: общий движок с vw-club.md/skoda-club.md, три отдельных репозитория и хостинга, копирование движка вместо submodule/пакета;
- read-only сайт: без логинов, без личного кабинета/«гаража»;
- контент-модель: frontmatter `model/engine/years/type`, авто-страницы `/models/[model]/`;
- название раздела статей — «Журнал»;
- дисклеймер «Не аффилирован с AUDI AG»;
- партнёрский промокод AUDICLUB15;
- бренд-направление: премиум/тёмный с красным акцентом, шрифт Inter;
- сохранение существующего логотипа клуба с адаптацией оттенка красного под акцент сайта.

Для каждого пункта, где нет однозначного источника (коммита, файла брифа, конкретной цитаты владельца), пометь ADR как `Статус: Принято (со слов владельца, без письменного источника на момент записи)` — не изобретай ссылки на несуществующие коммиты или строки кода.

Дальше — по мере реальной работы над кодом — на каждое архитектурное или продуктовое решение (даже небольшое: слаг, формулировка, структура коллекции) заводи новую запись ADR **в момент принятия решения**, а не пост-фактум пачкой.

## 4. Как вести оба документа дальше (это не разовое задание)

- Каждая сессия работы над проектом, где было принято архитектурное/продуктовое решение (новая страница, изменение структуры, отказ от какого-то подхода, смена контент-модели и т.п.) — заканчивается добавлением одной строки/секции в `DECISIONS.md` **до** завершения сессии, не «когда-нибудь потом».
- Если решение меняет структуру репозитория или переносит логику в другое место — обнови соответствующую строку в `PROJECT_MAP.md` §2/§3 в той же сессии.
- Если новое решение отменяет/заменяет старое — не удаляй старую запись ADR, помечай `SUPERSEDED ADR-XXXX`, как это сделано в bravo-motors (пример: ADR-0002 → ADR-0005).
- В начале каждой новой сессии с чистым контекстом (новый чат/новый экземпляр Claude Code) — первым делом открывать `PROJECT_MAP.md`, не читать весь репозиторий.
- Раз в несколько сессий (или когда дерево репозитория заметно разошлось с §2) — регенерировать дерево из `tree` и обновить `PROJECT_MAP.md`.
